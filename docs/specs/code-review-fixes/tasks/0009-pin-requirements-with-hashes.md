# Task 0009 — Pin `requirements.txt` with hashes; add `pip-audit` to CI

**Severity:** HIGH (supply chain + reproducibility)
**Source:** `docs/code-review-2026-05-08.md` cross-cutting theme #8, top-fix #9.
**Estimated effort:** Half day.

---

## Problem

`requirements.txt` is dangerously unpinned for a safety-critical CCTV monitoring system:

- `opencv-contrib-python>=4.11.0.86` — minor versions break CV pipelines.
- `ultralytics>=8.0.0` — YOLO API changed between 8.0 and 8.3; pose-keypoint indices have shifted in past releases.
- `fastapi>=0.104.0`, `pydantic>=2.5.0` — pydantic 2.x has had breaking minor releases in validators.
- `numpy>=1.26.0,<2.0.0` — OK upper bound, but not tied to mediapipe's actual ABI.
- **No `torch` / `torchvision` pin at all** despite `import torch` and CUDA build requirements. Whichever wheel ultralytics resolves is what you get. CLAUDE.md says CUDA 12.0 toolchain, RTX 4000 Ada — wrong torch wheel = silent CPU fallback.
- `pillow>=8.0.0` — allows known-vulnerable Pillow ≤9.x (CVE-2024-28219, etc.).
- `mediapipe==0.10.21` — only fully-pinned package. Inconsistent with the rest.

Result: two consecutive deploys on the same source produce different binary outputs. Diagnosing a behavior change becomes a forensic exercise.

## Files to change

- `requirements.txt` — replace with `requirements.in` (loose) + `requirements.lock` (pinned with hashes)
- `requirements.in` — **NEW**, the human-readable input
- `requirements.lock` — **NEW**, generated by `pip-compile`
- `Makefile` or `scripts/lock-deps.sh` — convenience target

- `start_server.sh:11-22, 56-57` — install from `requirements.lock`, drop the auto-`pip install` on every start (separate-task-like cleanup, but lands here)
- `deploy-gpu.sh` — same

### Lock generation

```bash
# scripts/lock-deps.sh
pip install pip-tools
pip-compile --generate-hashes --resolver=backtracking \
    --extra-index-url https://download.pytorch.org/whl/cu121 \
    -o requirements.lock requirements.in
```

Pinning torch via the PyTorch CUDA index is essential — the default PyPI wheel is CPU-only.

### Install command

Production, deploy, and dev all use:

```bash
pip install --require-hashes --no-deps -r requirements.lock
```

`--require-hashes` is the kill switch that rejects any tampered or unpinned install.

### CI gate

Add a workflow step:

```yaml
- name: pip-audit
  run: |
    pip install pip-audit
    pip-audit --requirement requirements.lock --strict
```

Failing on any HIGH or CRITICAL CVE.

### Start script cleanup

Remove the per-start `pip install` from `start_server.sh:11-22, 56-57`. Move dependency installation to a separate `setup.sh` invoked manually or by `deploy-gpu.sh`.

## Acceptance criteria

1. `requirements.lock` exists, is committed, contains `--hash=sha256:...` for every package.
2. `pip install --require-hashes -r requirements.lock` succeeds on a clean venv on the GPU box.
3. `pip-audit --requirement requirements.lock --strict` passes (or the failures are documented and approved).
4. `python -c "import torch; print(torch.cuda.is_available())"` prints `True` after install on the GPU box.
5. `start_server.sh` no longer runs `pip install` on every invocation.
6. CI runs `pip-audit` on every PR.
